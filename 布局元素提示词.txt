
🎨 前端 UI 与交互开发提示词 (Frontend Prompt)
角色： 资深 React/Next.js 前端工程师
任务： 开发“高铁基础布局施色域选择”交互页面
1. 布局要求
整体架构： 采用左右分栏布局。左侧为主操作区（占 75% 宽度），右侧为“已选配置清单”侧边栏（占 25% 宽度）。
风格指南： 参考已开发的页面
2. 核心功能组件
选择区域 (Configuration Group)：
按垂直方向排列多个分类（如：车窗带区域、车门区域）。
每个分类下横向展示配置卡片。卡片包含：高铁轮廓线稿图、名称、选中指示器。
互斥逻辑： 每个区域的卡片为“单选”关系，用户点击一个卡片即取消同组其他选中，再次点击可取消当前选中（即“选一或不选”）。
侧边栏 (Active Configurations)：
维护一个“方案列表”。
点击主区域底部的“完成”按钮，将当前选中的所有部位组合存入右侧栏，命名为“方案 1/2/3...”。
侧边栏卡片需展示该方案的缩略图概览。
3. 交互状态管理
默认状态： 首次进入页面，系统需默认选中第一套预设方案。
切换逻辑： 用户可以随时修改左侧选择。点击右侧已保存方案，左侧操作区应同步还原该方案的选择状态。
导出： 底部大按钮“下一步”在点击时，需聚合当前选中方案的 ID 数据。

⚙️ 后端架构与数据提示词 (Backend Prompt)
角色： 高级系统架构师
任务： 设计高铁配置选择系统的数据模型与 API 接口
1. 数据模型 (Schema)
Component (部位组件): id, category (如 window_area), name, image_url, vector_data (用于后续渲染)。
UserScheme (用户方案): id, user_id, name, components_map (存储格式：{category_id: component_id}), created_at。
2. API 接口定义
GET /api/components: 获取所有可选的形态分析部位数据（按类别分组）。
POST /api/schemes: 保存一个新方案。接收当前选中的组件 ID 列表，返回生成的方案 ID 和时间戳。
GET /api/schemes/{id}: 获取特定方案的详细配置，供前端回显。
3. 业务逻辑规则
合法性校验： 后端需验证同一 category 下不能出现多个 component_id。
默认方案生成： 系统需预置一个 is_default 标志位，确保用户首次调用能获取到初始形态配置。
数据聚合： 最后一个接口需能将选中的形态 ID 转化为用于 AI 渲染的语义化标签 (Tags)，例如：将“垂直强调式车门”转化为渲染 Prompt。
