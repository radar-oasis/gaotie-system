# 色彩方向与情绪板：现状核查及改造建议

日期：2026-09-16。状态：调研建议，待用户确认；没有改动功能代码、注册图库账户或调用付费模型。

## 研究范围与证据边界

要支持的决策：色彩模块是否从“布局区域施色”转为跨模块的色彩方向，以及图片输入、取色、配色与最终生成如何衔接。

证据：当前前后端代码；官方图库API及使用规则；W3C颜色规范；开源颜色库官方仓库。停止条件是能解释现有绑定、提出可实施的数据与职责分离、确认至少一个外部图片来源的公开接入路线，并明确未验证事项。不把库文档的功能宣称当作本项目效果测试。

尚未验证：国内实际网络可达性、具体文化主题的搜索质量、图库生产配额审批、候选配色的用户偏好、生成图遵守颜色约束的程度。以下效果均为设计预期，不是已实现效果。

## 一、核查结果：不是完全缺少取色，而是取色被放在区域填色流程中

- 前端 ImagePaletteExtractor 已支持单张上传，调用 /color-config/extract-palette；点击色块会更新当前选中的施色域。
- 后端用 sharp 将图缩至最大120×120，统计RGB量化色块，跳过透明像素、接近纯白与纯黑，返回频率最高的8种颜色。
- 配色仅以第一种提取色为基色，在HSL空间生成邻近、互补、对比和单色方案；不是多模态图像理解，也没有多图语义看板。
- 代码内没有发现外部图库搜索/情绪板实现。上传是一张图片状态，多图集合及图片权重尚未建立。
- 前端保存要求已选布局；后端保存要求layoutSchemeId及非空regions；最终生图指令要求“色彩必须按区域执行”。只换一个页面不够，需要同时变更保存模型和最终生成契约。
- 最终生成已有色卡图片制作能力，可以复用。但当前色卡是等宽色块，并不表达主辅色比例。

反例验证：用当前编译产物对内存生成的纯白和纯黑图片取色，两者均返回No usable colors extracted from image。对于需要白底、深色线条的涂装，这一过滤不能无条件沿用。建议保留中性色，并允许用户指定背景是否参与取色，而不是断言白色无价值。

## 二、建议：独立色彩方向，区域施色保留为可选精细模式

核心判断：缺少图库只是输入端的问题；真正造成冲突的是不同模块都在表达颜色，却没有统一的采纳规则。即使增加情绪板，如果最终指令仍强制按区域施色，冲突不会消失。

建议区分三个产物：

1. 情绪板：用户确认的参考图片、主题标签、来源及说明，回答“想要什么气质”。
2. 色板：从参考中提取或人为调整的颜色，回答“可以用哪些颜色”。
3. 配色方案：主色/辅助色/强调色/中性色、建议比例、明暗与饱和度关系、锁定项和解释，回答“如何组合使用”。

色彩方向属于项目，可先于或晚于布局建立。纹样转化与最终效果生成按需采用同一版本；不强制用户回到前一步，也不自动覆盖已生成资产。

对每个纹样明确：保留原色、允许向色板协调、仅参考形态。改色形成副本。最终生成前展示冲突摘要，建议约束次序：用户显式锁定项 > 本次采用的色彩方案 > 未锁定图片的附带颜色。同级显式要求冲突则由用户处理，不让提示词暗中裁决。

## 三、图片到方案的机制

### 输入与看板

三个入口使用同一图片资产结构：用户上传、项目已有纹样/画布素材、获准使用的外部图库。优先支持多图与框选取色区域；外部来源不可用时不阻断上传路径。

文化主题用于提出可编辑检索词，而不是直接固定颜色。“春节”可以建议灯笼、年画、节庆装饰等多个方向；用户确认图片后再做取色，避免预设红金筛选又反过来证明春节只能红金的循环。

从多个意象搜索时沿用独立分组，去除重复/近似图片并让不同来源有展示机会。用户先挑选少量参考，系统再按色调和主题整理看板。第一版情绪板用真实图拼贴与标签即可，无须先用生成模型画一张合成图片。

### 分离“像素事实”与“设计建议”

图像算法负责数值：统一到sRGB、处理透明度/旋转、按用户ROI采样、在感知颜色空间聚类、合并近似色，输出代表颜色、图内占比和来源区域。多图先各自归一化，再按图片权重组合，避免大图或大量近似图主导全部结果。

不直接从拼贴后的整张情绪板统计颜色，因为拼贴背景、标题与不同图片显示尺寸会改变频率。应分析原图/ROI，最后再排版看板。

采用Oklab/OKLCH或Lab做距离及明暗/彩度调整，回到sRGB时进行色域检查。颜色空间改善感知距离，但并不负责判断文化意义或美感。[W3C CSS Color 4](https://www.w3.org/TR/css-color-4/)

方案规则负责组织：保留参考中代表性的主辅色关系，产生忠实提取、协调变体和强调对比等少量不同候选。主色不一定是像素最多的颜色；背景可以面积很大，主题代表色可以很少。图内占比与未来涂装的建议比例必须分开。

同类色、互补色、单色、分裂互补等作为候选构造规则，不是“必然好看”的评分真值。主/辅/强调的比例可配置，60/30/10最多作为启发式起点，不是高铁涂装规范。[Adobe Color](https://color.adobe.com/create/color-wheel)

可选多模态模型负责理解图片主题、区分背景与主体、根据用户目标选择规则和解释方案。准确HEX与比例来自算法；模型引用色块ID，不凭描述编造取色结果。解释标记“原图提取”“算法调整”“用户指定”，不能把建议包装成历史文化事实。

### 现成组件

- [Material Color Utilities](https://github.com/material-foundation/material-color-utilities)：可参考量化、颜色评分、调和与色调生成，提供TypeScript实现；其UI配色角色不是车辆涂装标准，不应整套照搬。
- [Culori](https://github.com/Evercoder/culori)：颜色空间转换、色差、插值及色域处理，适合辅助现有TypeScript栈。
- [Color Thief](https://github.com/lokesh/color-thief)：浏览器/Node图片取色的备选，不等于完整的文化配色推荐系统。

不需要同时引入三个库；建议保留现有sharp作为图像解码层，选择一种量化实现和一种颜色运算路径做小样比较。

## 四、外部图库：可以接入，但不是任意网页抓图

推荐后端统一搜索适配层：主题词 → 官方搜索接口 → 标准图片卡片（来源ID、预览URL、原始页面、作者、许可、访问时间） → 用户选入看板 → 按权限取色/导出。API密钥留在后端；额度、超时、来源失效独立处理。

| 来源 | 定位建议 | 关键限制 |
|---|---|---|
| Pexels | 节庆、自然、现代摄影等参考候选 | 官方API需要密钥，遵守展示、署名及API使用要求；文化主题质量未实测 |
| Unsplash | 气氛与摄影素材候选 | API要求使用返回图片URL热链及署名，采纳/下载行为按官方要求处理 |
| Wikimedia Commons | 文化对象、建筑、器物等补充 | 按文件读取许可，可能需要署名、许可链接及相同方式共享 |
| The Met Open Access | 开放馆藏艺术与器物参考 | 筛选公共领域/OA且有可用图片的记录，不代表全站所有图片都可自由使用 |

官方来源：[Pexels API](https://www.pexels.com/api/documentation/)、[Unsplash API](https://unsplash.com/documentation)、[Commons使用规则](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia)、[Met API](https://metmuseum.github.io/)、[Met开放资源政策](https://www.metmuseum.org/hubs/open-access)。

图库定位是候选适配判断，不是已测得的覆盖率。不要一开始同时接四家。先用“春节、龙凤、青花瓷、山水”等固定查询验证有效结果、重复率、权限信息和网络响应，再选一个来源试接。

权限应分开评估：站内预览、临时取色、缓存原图、拼贴导出、发送外部模型。能显示不等于能执行其余动作；禁止模型训练也不能直接等同于禁止所有单次推理。未经核实的用途默认不开放，必要时向平台确认。首版最终生成优先只传色卡与用户确认的方案文字，减少原始参考图泄露及风格干扰。

不提供任意URL图片代理：若将来支持链接导入，要阻止私有地址及危险重定向、限制类型/尺寸/时长、执行项目权限校验，避免内网访问及图片解码风险。图片许可与人物/商标等其他权利仍需分别检查。

## 五、最小数据拆分与迁移

- Moodboard：projectId、主题、确认图片、图片权重、来源许可；作为可编辑集合。
- PaletteProposal：颜色ID/HEX/感知空间数值、角色、建议比例、来源、变换、解释及锁定项；不是布局的子记录。
- AdoptedColorDirection：项目采用的方案ID与版本、颜色强度、纹样保色策略。
- LayoutColorApplication：可选布局ID与区域覆盖规则，承接旧施色域方案。
- 生成记录保存当时采用的版本，防止后续改色造成历史说明与图片不一致。

旧记录保留：转换为带区域约束的兼容类型，不删除旧布局数据、不强行把用户原方案降为普通色板。项目快照和最终请求需要同时支持两类方案。

最终模型输入建议包括无字色卡、角色与目标比例说明、采用强度、保色例外；不默认把情绪板整张作为内容参考。没有必要向模型同时发送多套相互矛盾的方案。若要求精准区域色值，需要额外的区域后处理/矢量施色，不能只靠提示词保证。

## 六、路线选择与验收

路线A：仅解耦并支持上传多图/现有素材，取色+规则候选+最终采纳。依赖最少，先验证流程。

路线B（推荐）：A的基础上接一个官方图库，形成主题检索到看板到配色的完整体验。图库接入与色彩核心分离，无API时核心仍可用。

路线C：多源自动检索+多模态筛选/解释+进一步颜色重排。复杂度和评估成本较高，等B的素材质量及使用数据证明需要后再做。

首轮验收：没有布局也能保存/采用色板；上传多图能追溯取色色块；纯白/纯黑及透明图片行为明确；锁定的纹样不被静默覆盖；图库失败不阻断上传；未许可的导出不可操作；最终请求只有一套有效色彩规则并能复现历史版本。

效果评估需要真实用户比较候选采纳率、调整次数、找到满意方案的时间与最终图偏色。尚未做这些实验，不能声称新方案更美观。

可证伪判断：若用户实际都要求逐区域精准控制、无需提前探索色彩，独立色彩方向的收益会减小，应保留区域模式作为主用入口；但当前用户明确提出跨阶段配色需求，因此推荐独立方向作为默认。

Evolution Note：之后应复用“输入素材—提取事实—形成建议—显式采纳—下游执行”的分层，不再让一个模块同时决定颜色意义、区域位置和优先级。下一步是确认默认采纳策略及首个图库，然后再形成实现计划。
