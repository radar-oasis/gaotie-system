# 提示词增强的规则、构成与验证：增量核验

日期：2026-09-16。续接上一份画布提示词调研；只读查阅官方代码、论文和评测脚本，未运行模型或修改业务代码。

研究问题：哪些规则实际存在、为什么制定、拆解粒度是什么、验证究竟验证了什么。停止条件为覆盖规则式与训练式增强、文本与图片两级评价、至少三个独立项目，以及不适用于本系统的反例。注意：本文的设计解释不等于项目作者逐条做过消融实验。

## Prompt Optimizer：编辑操作与边界优先

当前 develop 的图生图模板先区分添加、删除、替换、增强，默认保留未提及元素；细化目标对象、位置、范围和变化程度，保持风格/色彩/透视一致，输出简短自然语言。包含占位符原样保留、避免凭空加入平台参数等规则。

它实际拆解的不是固定的“主体+背景”填空题，而是“原图状态—用户想改变的状态—保留范围—执行方法”。目的在于防止把用户期望的元素误认为原图已有，也防止局部编辑变成整张重画。为什么每条规则有效，源码只给设计意图和例子，不能说每条都有独立实验支持。

反例：模板对简洁单物偏好接地阴影，且默认保留原图构图。这对商品编辑可以合理，对从器物图中提取独立纹样未必合适；我们需要明确去掉载体背景、保留母题身份，而非保留整张原图。

来源：[实际图生图模板](https://github.com/linshenkx/prompt-optimizer/blob/develop/packages/core/src/services/template/default-templates/image-optimize/image2image/image2image-optimize.ts)。

评价有三个不同层次：

- [图生图提示词诊断](https://github.com/linshenkx/prompt-optimizer/blob/develop/packages/core/src/services/template/default-templates/evaluation/image/image2image/evaluation-prompt-only.ts)：修改意图明确性、细节指导准确性、风格与约束明确性、改进程度。模型输出分数与建议，不是实际图像成功率。
- [文生图单结果评价](https://github.com/linshenkx/prompt-optimizer/blob/develop/packages/core/src/services/template/default-templates/evaluation/image/text2image/evaluation-result.ts)：原始意图、实际发送文本和生成图共同参与；评价意图实现、画面忠实、提示词有效、可控性。特别区分提示词缺失与模型没有执行清晰指令。
- [文生图多结果对比](https://github.com/linshenkx/prompt-optimizer/blob/develop/packages/core/src/services/template/default-templates/evaluation/image/text2image/evaluation-compare.ts)：以原始意图为标准，不以优化文本新增的细节为标准，不默认优化版本获胜。

限制：有评估功能不等于该工具已有独立、代表性的效果基准。此次核验材料未提供足以证明纹样转化提升的受控实验；单图也不能真正测出稳定性，需重复采样。上述图像单结果/比较模板属于文生图，不应说所有编辑模式都有完全相同的已接通流程。

## Qwen：按任务类型选择需要补充的字段

官方工具区分文本扩写和图片编辑增强。编辑规则要求明确任务、对象、位置/数量/属性；输入已经明确时只整理表达，模糊时做最少必要补充；文字内容保持原文；风格转换说清视觉特征；多图表述明确来源角色；人物编辑注意身份一致性。不是每次都填满所有字段。

为什么这样做：减少指代和属性歧义，例如颜色属于哪一个对象、图2贡献主体还是风格。固定任务措辞和少量示例属于引导模型的经验规则，并非通用语法标准。

反例：文本扩写中的电影感补词、去否定表达等，不应套用到需要保留硬约束的纹样任务。规则写进系统提示词只是要求，不是程序能保证模型一定遵守。

验证边界：此次查到的是公开重写实现和示例，没有在该工具文件中找到独立的增强前后受控评测。Qwen 整体生成/编辑模型的成绩不能直接归功于这个小型重写工具。

来源：[官方 prompt_utils.py](https://github.com/QwenLM/Qwen-Image/blob/main/src/examples/tools/prompt_utils.py)。

## Hunyuan：从失败类型拆成可验证的关键点

依据 [arXiv v5 Table 1](https://arxiv.org/html/2509.04545v5#S2.SS4)，六类共24个关键点如下。它们是评价分类，不是要求每条提示词写满24项：

| 大类 | 关键点（中文归纳） |
| --- | --- |
| 语言理解 | 否定、同一属性作用于多个对象、代词指代 |
| 视觉属性 | 数量、大小、材质、表情、艺术风格 |
| 动作与互动 | 全身动作、手部动作、动物动作、接触互动、非接触互动、状态 |
| 关系与结构 | 比较、组成、包含、形状相似、跨实体属性绑定、实体布局 |
| 世界知识与推理 | 知识应用、反事实场景 |
| 图中文字 | 文字内容、文字布局 |

训练逻辑：先用优质改写示例训练重写器，再让候选重写真正驱动冻结的生图模型生成图片，由 AlignEvaluator 给出细粒度奖励，用 GRPO 更新重写器。它优化的是重写器，生图器不随之更新；这是训练阶段机制，不表示用户每点击一次增强就会现场训练和反复生图。

为什么不用单一美学分：好看的图仍可能画错数量、配错颜色或忽略否定。把这些分别检查，反馈才能告诉系统错误在哪里。本文归纳：优化目标是减少意图丢失，而不只是提高画面美感。

论文评测集为6,687条中英文需求；v5实验固定使用 HunyuanImage 2.1。论文报告24类平均提升约5.1个百分点，20类提升、2类持平、2类下降。这是特定模型与基准的作者报告，不是我们复现结果，也不是图生图编辑版或传统纹样的已验证收益。[论文实验](https://arxiv.org/html/2509.04545v5#S5)

当前 [公开评测脚本](https://github.com/Hunyuan-PromptEnhancer/PromptEnhancer/blob/main/t2i_keypoints_eval.py) 默认用 Gemini-2.5-Pro 对“原始需求、生成图片、单项考点”判断 accept/reject，统计逐考点和整图全部考点通过率。脚本的重写/生图函数需要自行接入，不能直接运行就得到完整复现。这个测试裁判不等于训练奖励模型 AlignEvaluator；模型评分也不等于人类评价。

补充证据限制：人工看图筛选确实参与训练数据构建，但本轮未在论文正文找到独立人类A/B试验的完整人数、胜率与一致性报告，不能宣称人工盲测胜出。公开脚本把裁判调用失败或无法解析也计为0，正式实验应分离服务失败；原始数据类别与论文24类需做明确映射才能对齐统计。论文训练轮数的正文与Table 2存在冲突，本文不采用其中任一组数值作确定复现配置。

## Promptist：一个有人工对照的补充参照

早期 Promptist 将提示词分成核心内容与风格修饰，使用人工编写示例训练，之后以图文相关性和美学评分优化。论文另请3位独立标注者比较原始/优化提示词生成的图片组偏好，说明作者也承认自动评分不能完全代表人类满意度。它的验证路线值得借鉴，但针对旧版 Stable Diffusion，不能据此确定当前系统收益。[原论文§2与§3.4](https://arxiv.org/html/2212.09611)

## 对项目的判断与可证伪方案

建议把单次纹样转化需求拆成：来源图及角色、保留项、修改对象/动作、变化方向与程度、图形组织、输出用途与边界。颜色、连续拼接、线描等只在相关时补充；不要为了结构完整硬塞与任务无关的摄影字段。

评测标准来自用户原始要求和用户确认的选择。例如用户选择“保守转化、保持颜色”，才可把保持颜色当作其认可的标准；不能让增强器擅加蓝色再奖励蓝色结果。开放探索任务同时看用户是否找到可用方向，不只看是否符合某一固定答案。

可操作的低成本验证：同一批任务对比原文、通用API改写、领域约束API改写，保持生图配置一致并重复生成；自动检查字段和长度，人工检查生成图的母题可识别、变化是否到位、颜色等明确条件是否保留、背景与边缘是否可用。评分人不预先知道哪个是增强版；留出不用于调规则的题目，记录失败案例。若增强降低保真或不能提升可用比例，就推翻“越具体越好”的假设。

修正上一轮概括：开源工具并非都只做文本自评，Prompt Optimizer 也有实际生成结果和多方案比较模板；但“具备评价机制”仍不能写成“已经证明普遍提升”。
