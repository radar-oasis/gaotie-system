# 高铁涂装人机共创系统：AI 产品经理简历项目叙事设计

## 1. 写作目标

将现有口语化的“背景—目标—难点—判断—动作—结果—复盘”材料，重构为一份面向 AI 产品经理求职的项目说明。成稿既能直接提炼进简历，也能支持面试时完整讲述项目从 0 到 1 的推进过程。

成稿不逐条复述或映射某一家公司的职位描述，而是在项目事实中自然体现 AI 产品经理的通用能力：用户洞察、复杂问题拆解、产品判断、AI 能力边界设计、Prompt 与上下文设计、领域知识检索、多模态生成、工作流编排、评测与 bad case 思维、跨角色协同以及借助 AI 工具完成原型落地的能力。

## 2. 产品定位

系统定位为“面向轨道交通文化主题涂装的知识驱动型人机共创工作台”，服务轨道交通视觉设计师从模糊文化主题到可讨论涂装方案的全过程。

系统不是单句 Prompt 生图工具。核心产品判断是：专业创意任务的主要矛盾并非单张图是否足够精美，而是如何让 AI 在文化语义、专业结构和用户意图约束下参与创意形成，并让设计师在关键节点保持判断权和最终责任。

## 3. 核心叙事

成稿以一条完整的 0 到 1 链路组织：

1. 从专家访谈、文献研究与竞品研究中识别问题：资料分散、文化意象到现代设计之间存在断层、直接生图容易元素堆砌和设计固着、车身结构约束难以进入生成过程。
2. 将问题抽象为“文化语义转译、专业约束注入和设计师主导权”三个产品命题。
3. 明确人机分工：AI 负责解析、发散、检索、局部转化、设计包整合和候选生成；设计师负责目标确认、文化判断、素材筛选、布局与色彩决策、结果评价和最终确认。
4. 把文化主题涂装流程产品化为七个连续模块：文化主题解读、纹样检索、纹样转化画布、车身布局、色彩配置、涂装案例和效果生成。
5. 通过双知识图谱、结构化设计包和多模态参考图，将一次性 Prompt 改造成可控、可追溯、可回退的分阶段工作流。
6. 借助 AI 编程工具完成 React、NestJS、PostgreSQL、Neo4j 与多模型服务集成，并通过测试、错误处理和版本归档提高原型稳定性。
7. 以形成性、定性反馈总结当前验证，不把尚未执行的定量实验写成已完成成果。

## 4. AI 产品能力的表达方式

### 4.1 Prompt 与结构化输出

- 为文化主题解读设计角色、任务流程、领域边界、反例和标签输出协议，将模糊主题转为前端可识别的意象标签。
- 为知识图谱检索设计 Schema 约束与 JSON 输出协议，将自然语言需求转为纹样、朝代、材质等结构化查询条件。
- 为最终方案生成设计分层提示模板，分别注入设计目标、车身布局、区域色彩、纹样、案例参考和用户补充要求。

### 4.2 上下文、知识检索与项目记忆

- 使用传统纹样知识图谱和轨道交通案例知识图谱提供领域上下文，降低通用模型的文化臆想与场景失配。
- 将需求标签、素材、布局、色彩、案例说明和画布截取组织成结构化设计包，在跨阶段传递用户意图。
- 通过项目快照、对话记录、方案归档和版本信息保存工作状态；准确表述为产品级项目记忆与上下文管理，不夸大为模型长期记忆。

### 4.3 多模态与工作流编排

- 将文本、纹样图、画布截取、布局参考图、区域色卡和案例图组合为多模态输入。
- 根据输入是否变化区分重新生成与基于上一版微调，避免把所有操作压缩为同一种生成行为。
- 通过人工确认节点控制工作流：AI 提供候选，设计师筛选、调整和归档。

### 4.4 评测与 bad case

- 重点分析文化元素堆砌、布局编号进入画面、车体结构变形、颜色区域错配、纹样与案例参考被模型错误复刻、过早收敛造成设计固着等 bad case。
- 评价框架覆盖结果质量与协作过程：文化契合度、车身适配性、美观完整度、创新性、可解释性、控制感和方案所有权。
- 当前只写形成性定性反馈；后续可开展“单句 Prompt 与结构化设计包”的对照实验，但不表述为已经完成。

## 5. 可使用的真实量化事实

成稿仅使用可由现有项目文件支持的数字：

- 12,000+ 张传统纹样图片；
- 传统纹样知识图谱包含 13,875 个节点、59,191 条关系；
- 轨道交通案例库收录 80 辆列车案例；
- 7 个核心设计模块；
- 双知识图谱与一套跨阶段结构化设计包；
- 前后端现有 40+ 个测试文件，可概括为围绕核心流程建立自动化验证，但不把文件数量包装成产品成效。

## 6. 验证边界

当前结果只采用以下表述：

> 通过与轨道交通涂装相关设计人员的阶段性走查与演示反馈，初步确认分阶段流程能够缓解面对空白需求时的无措感，知识图谱与候选素材有助于拓展文化意象，人工筛选、画布编辑和方案归档增强了过程控制感；同时暴露出生成稳定性、车身区域约束和交互学习成本仍需继续优化。

禁止写入未经真实执行支持的样本人数、评分均值、提升比例、显著性结果或“验证系统显著有效”等结论。

## 7. 最终 Markdown 结构

1. 项目名称、角色、周期与一句话定位；
2. 简历可直接使用版：4 至 6 条高密度项目经历；
3. 完整项目说明：系统是什么、为谁解决什么问题；
4. 背景、目标、难点、判断、动作、结果、复盘；
5. 从 0 到 1 的关键决策与产品演进；
6. AI 能力设计与工程落地；
7. 评测思路、bad case 与定性反馈；
8. 面试讲述版本；
9. 事实边界与后续可补充的数据清单。

## 8. 文风与事实规则

- 使用产品语言和行动语言，删除“这个、然后、其实、就是说”等口语填充词。
- 强调个人主导动作，但不虚构团队规模、商业收入、用户增长或上线规模。
- 技术名词服务于产品判断，不堆砌模型和框架名称。
- 区分“研究提出”“系统已实现”“阶段性走查反馈”和“后续验证计划”。
- 所有简历表述都应能够根据仓库、研究材料或本人真实经历在面试中展开说明。
